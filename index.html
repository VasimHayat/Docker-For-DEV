Docker for developers

Package an app once with everything it needs, and run it the same way on your laptop, a teammate's machine, and production. Here's the working knowledge, with examples you can paste.

zsh — ~/app 
$ docker run -d -p 8080:80 nginx
a1b2c3d4e5f6  ·  container started
$ curl localhost:8080
<title>Welcome to nginx!</title>

Why containers

"It works on my machine" happens because software depends on more than its own code — a specific language version, system libraries, environment variables, a database. A container bundles your app together with all of that into one runnable unit, so the environment travels with the code.

Virtual machine

Ships a whole guest operating system per app. Heavy — gigabytes of RAM and disk, slow to boot.

Container

Shares the host's kernel and isolates just your app. Megabytes, starts in milliseconds, dozens run side by side.

Core concepts

Six words cover almost every conversation about Docker. Learn these and the commands read like English.

image
A read-only blueprint — your app plus its dependencies, frozen. Built from a Dockerfile.
container
A running instance of an image. You can start many containers from one image.
Dockerfile
A recipe of instructions that tells Docker how to build an image, step by step.
registry
Where images live and are shared — Docker Hub is the default public one; teams run private ones.
volume
Storage that outlives a container, so data (like a database) survives restarts and rebuilds.
network
A private bridge that lets containers find and talk to each other by name.

Essential CLI

You'll use these every day. The pattern is always docker <verb> <target>.

run — start a container from an image 
$ docker run -d -p 3000:3000 --name web myapp
# -d detached · -p host:container ports · --name friendly handle
ps / images — see what's running & what's built 
$ docker ps -a          # running + stopped containers
$ docker images         # images on this machine
exec / logs — get inside & debug 
$ docker exec -it web sh   # open a shell inside container "web"
$ docker logs -f web       # stream its output
stop / rm / pull — lifecycle 
$ docker stop web        # graceful shutdown
$ docker rm web          # remove the container
$ docker pull postgres:16 # fetch an image from the registry

Writing a Dockerfile

A Dockerfile turns your source into an image. Below is a production-ready multi-stage build for a Node.js/Express app: one stage installs and builds, a second, lean stage ships only what's needed to run.

Dockerfile 
# ---- stage 1: build ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- stage 2: run ----
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
  • FROMthe base image to start from; -alpine keeps it tiny.
  • COPY packagecopy manifests first so npm ci is cached until deps change.
  • --from=buildpull only built artifacts into the final image — build tools stay behind.
  • USER noderun as a non-root user; never ship a container running as root.
  • CMDthe default command that runs when the container starts.

Pair every Dockerfile with a .dockerignore. It keeps junk out of the build context, so builds are faster and secrets never sneak into an image.

.dockerignore 
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
dist
coverage
Dockerfile
.dockerignore
*.md

Ignoring node_modules matters most: you install fresh inside the image with npm ci, so copying the host's copy would only bloat the context and risk platform-mismatched binaries. Excluding .env keeps credentials out of the image.

Build & run

Two steps: build the image from the Dockerfile, then run a container from it.

  1. 1 build the image, tag it "myapp" 
    $ docker build -t myapp:1.0 .
# -t names/tags the image · "." is the build context (current dir)
  2. 2 run it, mapping a port 
    $ docker run -d -p 3000:3000 --name web myapp:1.0
$ open http://localhost:3000

Docker Compose

Real apps are more than one container. Compose describes the whole stack in one YAML file and starts it with a single command. Here's a web app wired to a Postgres database.

docker-compose.yml 
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
start & stop the whole stack 
$ docker compose up -d     # build + start web and db in the background
$ docker compose logs -f    # follow logs from every service
$ docker compose down       # stop and remove everything (volumes persist)

Note how web reaches the database at hostname db — Compose puts both on a shared network and resolves service names automatically.

Volumes & persistence

Containers are disposable — delete one and its internal files vanish. Anything that must survive (databases, uploads) belongs in a named volume that Docker manages outside the container.

persist Postgres data across restarts 
$ docker volume create pgdata
$ docker run -d -v pgdata:/var/lib/postgresql/data postgres:16
# -v volume:path mounts managed storage into the container

Networking

Each container gets its own isolated network stack. To let containers talk, you put them on the same user-defined network, where Docker runs a small DNS resolver so they can find each other by name — no hardcoded IPs.

bridge

Default. A private virtual network on one host. User-defined bridges add name-based DNS.

host

Shares the host's network directly. No isolation, no port mapping — fastest, least safe.

none

No networking at all. Fully isolated — useful for untrusted or offline workloads.

put two containers on one network, talk by name 
$ docker network create appnet
$ docker run -d --network appnet --name db postgres:16
$ docker run -d --network appnet --name web myapp
# "web" now reaches Postgres at the hostname "db" — Docker's DNS resolves it
inspect the network & publish a port to the host 
$ docker network inspect appnet  # subnet, gateway, connected containers
$ docker run -d -p 8080:80 --network appnet nginx
# -p publishes to the host; without it, a port is reachable only inside the network

Rule of thumb: containers on the same user-defined network reach each other on their internal ports by name. You only need -p when something outside Docker — your browser, another machine — needs in. This is exactly what Compose does for you automatically.

Best practices

Start small

Prefer -alpine or -slim base images. Smaller images build, push, and boot faster.

Use a .dockerignore

Exclude node_modules, .git, logs. Keeps the build context lean and builds quick.

Order for caching

Copy dependency manifests and install before copying source, so code edits don't bust the dependency layer.

Never run as root

Add a USER instruction. If the container is breached, the blast radius stays small.
